An experienced specialist contributes more than remembered information. They know which conditions matter, when more evidence is needed and when an initial explanation should be rejected. Helping agents reuse that expertise requires organizing knowledge, methods and the boundaries of judgment together.

A knowledge base is a starting point. Retrievable documents establish access to information. How that information is used, how results are verified and how method changes are controlled still require deliberate design.

## Turn knowledge into methods with conditions

In reliability assessment, “check retry risk” is a reminder. An executable method must also specify which call boundaries to examine, which configuration version is relevant, how to correlate one business operation, what supports a conclusion about amplified calls and what is needed to establish repeated business effects.

A maintainable method includes its purpose, prerequisites, inputs, procedure, criteria, counterexamples and sources. Handling unknown outcomes is part of the method. Agents can then work within professional constraints rather than invent missing rules from a description of past experience.

Engineering articles and assessment reports can supply useful structures. A new domain still requires its own semantics. Rules for financial reconciliation cannot determine whether a procurement approval is appropriate.

## Bind methods to task versions

Knowledge can be maintained in a readable, comparable format such as Markdown. Task state, tool execution and evidence indexes have separate recording responsibilities. The essential requirement is knowing which method version a task actually used.

Editing a knowledge file should not silently change the rules for work already in progress. New material becomes a candidate version. Existing tasks retain their version or migrate under explicit, recorded conditions. When two tasks reach different conclusions, version history helps distinguish changes in inputs, methods and execution.

This also makes expert review concrete: which check was added, which condition was removed, and did the handling of failure or uncertainty change?

## Evaluate before adopting a change

Evaluation should cover ordinary inputs, known problems, incomplete material, misleading counterexamples and unavailable tools. Run candidate and current methods under comparable conditions. Keep actual outputs, verification evidence, human review and total effort.

Reading more documents does not establish improved capability. Improvement by one role on one task does not demonstrate improvement across roles or domains. Independent review should examine whether the method improved judgment, introduced omissions or added costs that outweigh its benefits.

The decision may be to adopt, revise or retain the previous version. Reverting a method changes how future work is conducted; it does not automatically undo business actions that have already occurred.

## Make capability profiles point to evidence

A team can organize role assessments around domain knowledge, analytical judgment, execution and delivery, quality and risk, and collaboration. These dimensions help identify gaps. They should not manufacture a precise-looking aggregate score.

Each assessment should identify applicable tasks, evidence, date and missing capability. Without evaluation, the status remains unassessed. Labels such as “expert” need a defined scope. Periodic review should first check whether knowledge, tools or the relevance of existing evidence have changed, then identify the learning and verification required.

## Build on existing engineering practice

Smartscity's reliability assessment methods organize work around checks, evidence and conclusions. Reports separate overall judgments from detailed support. This professional foundation can inform agent methods; a report template does not establish the agent's diagnostic ability.

The current agent project has explored local role learning and method comparison. Some method updates have comparative evidence, while role extension, knowledge version management and capability assessment remain under development. Enterprise adoption still needs evidence on the customer's own tasks. Local exploration is not a mature governance product.

A useful pilot has recurring professional work, accessible method sources and an expert willing to define acceptance. For example, choose one class of change assessment, establish the current method as a baseline, and compare a candidate improvement on effectiveness and maintenance effort.
